- Unveränderter Produktionsbuild vor der Änderung: `PATH=/tmp/ygh-p201-node/node-v24.22.1-darwin-arm64/bin:$PATH npm run build` → erfolgreich. Das war nur die Ausgangsprüfung, kein Nachweis der noch nicht implementierten lokalen Buildgrenze.
- `npm run typecheck` → erfolgreich.
- `npm run lint` → erfolgreich.
- `npm test` → 10 Testdateien bestanden, 2 übersprungen; 37 Tests bestanden, 6 Linux-spezifische Tests übersprungen. Das entspricht den in der Entwicklungsanleitung genannten macOS-Grenzen.
- `npm run build` nach der Änderung → erfolgreich; Next.js meldete zusätzlich, dass die `package.json` im übergeordneten Ordner außerhalb des Git-Repositories für Turbopack ignoriert wurde.
- `node scripts/test-local-production-boundary.ts` gegen `.next/standalone/server.js` → bestanden: bei gesetztem `YGH_LOCAL_DEV_USER=admin`, Laufzeit-Opt-in und geändertem `NODE_ENV=development` wurde die lokale Identität trotz vorhandenem synthetischem Benutzer, exaktem Host `127.0.0.1:3001` und gültigem Tailscale-Header abgewiesen. Der normale Tailscale-Identitätspfad desselben Builds wurde mit einem isolierten Testbenutzer zugelassen. Für den kurzen Loopback-Server war eine genehmigte Sandbox-Eskalation erforderlich.
- `docker compose -p ygh-local -f compose.local.yaml config --quiet` → erfolgreich. Gerenderte Konfiguration bindet ausschließlich `127.0.0.1:3001`, verwendet `/data/collection-local.sqlite` und das getrennte Volume `ygh-local_local-data`; persönliche Tailscale- und `APP_ORIGIN`-Werte werden nicht übernommen.
- Browserprüfung im Docker-Stack → Admin- und Mitgliederrolle, Reload und die drei PNG-Icons (HTTP 200) bestanden. `localhost:3001` wurde trotz aktivem Admin abgewiesen. Nach der engen `allowedDevOrigins: ["127.0.0.1"]`-Freigabe für ausschließlich die Next-Entwicklungsphase verband sich HMR und zeigte eine Quelltextänderung ohne Reload oder Neubau.
- Datenbankprüfung im laufenden Container → deaktivierter Admin wurde abgewiesen; Containerneustart ließ `active=0` bestehen. Anschließend wurde ausschließlich der synthetische Testbenutzer wieder auf `active=1` gesetzt. Fremde Hosts wurden abgewiesen. Fremde bzw. unvollständige Datenbanken werden zusätzlich in `scripts/local-dev-init.test.ts` mit unverändertem Datei-Hash beziehungsweise erhaltener Benutzerzahl geprüft; ein Dockerlauf gegen eine fremde Datenbank wurde nicht ausgeführt.
- `git diff --check` → erfolgreich.

Ein erster Volltestlauf hatte einen Banner-Testfehler, während die separate HMR-Browserprüfung vorübergehend einen anderen Text in `src/app/page.tsx` einsetzte. Root stellte die Datei byteweise auf den vorherigen Stand zurück; der erneute Volltestlauf bestand vollständig. Der temporäre Prüfinhalt ist nicht im Arbeitsstand enthalten.

## Unabhängiger Review

Der Hauptagent prüfte den tatsächlichen Code und die Testbedingungen gegen E09. Die vorherigen Änderungen an Katalogschema, Migrationen und Katalogtests blieben nach Hashvergleich mit der vor Implementierungsbeginn erstellten Dateiliste unverändert; keine Manifest-/Lockfileänderung. Die bereits vorhandene Dokumentationspflege wurde erhalten.

Gezielte Nacharbeit aus dem Review:

- Der erste Produktions-Negativtest hätte auch an fehlender lokaler Testidentität oder einem abweichenden Host scheitern können. Er enthält nun beide lokalen Identitäten und sendet den exakten erlaubten Host; zusätzlich prüft er die Sperre trotz eines gültigen Tailscale-Headers. Damit werden diese unabhängigen Fehlerursachen als Scheinerfolg ausgeschlossen.
- Explizit leere lokale Rollenwerte werden nicht mehr durch Compose zum Adminstandard umgedeutet. Das neue Loggerfeld akzeptiert nur die festen Moduswerte.
- Der praktische Browser-Test deckte die blockierte HMR-Verbindung auf. Eine exakte Entwicklungs-Origin-Freigabe behob dies; keine Wildcard und keine Erweiterung der Server-Action-Allowlist. Im fertigen Produktionsartefakt ist die lokale Buildkonstante `false` und die zusätzliche Entwicklungs-Origin-Freigabe fehlt.

Unabhängig wiederholt: `npm test -- src/server/auth/index.test.ts src/server/access.test.ts scripts/local-dev-init.test.ts src/app/page.test.tsx` → 26 Tests in vier Dateien bestanden. `node scripts/test-local-production-boundary.ts` → beide Fälle bestanden. Die oben beschriebenen Docker-/Browserprüfungen führte der Hauptagent selbst aus. Der Produktionsbuild wurde von Luna ausgeführt und anschließend dessen tatsächliches Standalone-Artefakt unabhängig getestet; kein zweiter Root-Build behauptet.

Keine offenen Implementierungsbefunde im Umfang von P1-16.
